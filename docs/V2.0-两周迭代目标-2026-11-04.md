## 0. 目标重述（一句话）

> **让一个刚学会用 AI 写代码、但看不懂报错的人，在 3 分钟内搞清楚：这是什么错、为什么会错、我要先懂哪些概念、去哪儿学、现在该做什么。**

软件不是"给 AI 递证据"的工具，是**新手读报错的翻译器 + 导学地图**。

## 1. 目标用户与核心 KPI

### 1.1 用户画像

| 类型 | 特征 | 他缺什么 |
|---|---|---|
| **A. Vibecoding 新人** | 靠 AI 生成代码，能跑起来但一报错就懵；不认识术语 | 缺「这是什么」的定性 + 缺术语翻译 |
| **B. 转行学习者** | 正在学编程，认识语法但不理解运行时错误 | 缺「为什么会错」+ 缺概念体系 |
| **C. 半路接手的开发** | 会一点，但对陌生框架/语言的报错没底 | 缺「这个场景下通常怎么排查」 |

三类人共同点：**不是要一份结论，是要"看懂"这件事本身。**

### 1.2 核心 KPI（V2.0 上线后要能回答）

| KPI | 定义 | 目标 |
|---|---|---|
| **术语零门槛** | 新人版解释中，未加解释的专业术语数量 | 0 |
| **看懂率** | 用户自评「懂了」占比 | ≥ 70% |
| **行动转化率** | 看完结果后点击「下一步」或「学习资料」的比例 | ≥ 50% |
| **学习闭环率** | 被推荐资料中，用户点击/收藏/标记已学的比例 | ≥ 30% |
| **二次求助率下降** | 同一新人重复提交同类报错的比例 | 逐版本下降 |

> 这 5 个指标就是 V2.0 说明书里「软件价值」一节的量化依据，也是软著材料里最能体现独创性的部分。

### 1.3 从 KPI 反推功能（对齐表）

| KPI | 对应能力 | 归属 |
|---|---|---|
| 术语零门槛 | 术语降维 + 分层解释 | P0 |
| 看懂率 | 场景补全 + 看懂度反馈 | P0 |
| 行动转化率 | 下一步清单（可勾选） | P0 |
| 学习闭环率 | **学习资料挂载 + 概念图谱** | P1 |
| 二次求助率下降 | 相似案例推荐 + 知识沉淀 | P2 |

## 2. 现状 vs 目标：解释链路逐环体检

一条完整的「让新人看懂」链路应该有这么 8 环，现状逐环打勾：

| # | 环节 | 现状 | 差距 |
|---|---|---|---|
| 1 | **这是什么错**（定性） | ✅ 有一句话定性 + 生活类比 | — |
| 2 | **它出现在哪一步**（场景） | ⚠️ 只有"出在哪一层"（业务/框架/基础设施），是**技术分层**不是**操作场景** | 新人不知道"我在做哪一步时错了" |
| 3 | **为什么会错**（人话原因） | ✅ 有"疑似技术使用不妥" | 但只给方向，缺"新手最常犯的 2-3 个具体错误" |
| 4 | **这个陌生的词是什么** | ❌ 无 | 新人卡在 `NullPointerException`、`依赖注入`、`连接池` 这些词上 |
| 5 | **我要先懂哪些概念** | ❌ 无 | 没有概念前置关系，不知道从哪学起 |
| 6 | **去哪儿学** | ❌ 无 | **本稿新增的重点能力** |
| 7 | **现在该做什么** | ⚠️ 有一句"复制诊断包发给项目 AI" | 对新人来说这等于"我也不知道，你问别人" |
| 8 | **我讲明白了吗** | ❌ 无 | 没有反馈，解释质量不可迭代 |

**结论：8 环里 3 环完全缺失、2 环偏弱。** 现在的产品是一只"解释一次就结束"的喇叭，不是"陪你把这件事搞懂"的导学系统。

## 3. V2.0 设计

### P0：解释质量链路（核心，3.5 天）

**目标：把"解释"从一段文字，拆成新人能逐环走下去的 5 步。**

#### P0-1 分层解释（新人版 / 进阶版）

- 契约扩展 `PreTriageReport`：

```json
{
  "personReport": {
    "plain":  { "summary": "...", "scene": "...", "reason": "...", "nextStep": "..." },
    "detail": { "summary": "...", "layer": "...", "misuse": "...", "nextStep": "..." }
  },
  "handoff": { ... },
  "concepts": ["空指针", "依赖注入"],
  "commonMistakes": ["...", "..."]
}
```

- **一次 AI 调用同时产出两档**（不是调两次，省 token；这是设计取舍，可写进说明书）
- 新人版硬约束（写进提示词）：**不得出现任何未经解释的专业术语**，必须用生活场景类比
- 进阶版：保留术语，但每个术语首次出现自动加「?」气泡（见 P0-2）
- 前端：结果卡片顶部 `Segmented` 切换「新人版 / 进阶版」，默认新人版

#### P0-2 术语降维与类比库

- 新增表 `glossary_term`：`term / plain_def / analogy / example / language / category`
- 种子 50+ 条（空指针、依赖注入、连接池、递归、序列化、异步、索引、闭包……）
- **文本后处理**：解释文本渲染前，扫描术语表，命中则包成可 hover 的 `<Term>` 组件，悬浮显示「人话定义 + 类比」
- 这解决一个真实痛点：AI 就算解释得不错，也总会漏掉几个术语

#### P0-3 场景上下文补全

- 新增字段：`scene`（这种报错通常出现在什么操作场景）+ `commonMistakes[]`（新手最常犯的 2-3 个具体错误）
- **离线兜底**：内置「异常类型 → 场景」映射表（约 30 条），无 AI Key 的 Mock 模式也能给场景，保证演示完整

#### P0-4 下一步行动清单

- 结构化 `nextActions: [{ order, action, why, type(check/fix/learn) }]`
- 前端渲染成可勾选 checklist，勾选状态存本地
- 关键改动：把"复制诊断包给项目 AI"从**唯一出路**降为**其中一步**，前面先给新人能自己做的事

#### P0-5 看懂度反馈闭环

- 结果卡片底部：「看懂了吗？」→ 懂了 / 部分懂 / 没懂
- 没懂 → 提供「换个说法再讲一次」（更浅档位重生成，走轻量提示词）
- 数据落 `triage_feedback`，作为 P3 质量看板与资料推荐的依据

### P1：学习资料挂载与概念图谱（新增重点，3.5 天）

> 这是本稿的核心增量。目标：**每条解释旁边，挂上一套"想彻底搞懂就看这些"的资料。**

#### 3.2.1 设计思想：不是"链接列表"，是"概念图谱驱动的导学"

单纯的"相关链接"没有价值（谁都会搜）。真正有价值的是：

> **先判断"要理解这个报错，你得先懂哪几个概念"，再按概念的依赖顺序，推荐对应的资料。**

所以系统有三个核心对象：

```
异常 ──(AI/规则)──▶ 概念 ──(前置关系)──▶ 概念学习路径 ──▶ 资料
                    ▲
              concept_edge 有向图
```

#### 3.2.2 数据模型

**表 1：`learning_resource`（学习资料）**

| 字段 | 说明 |
|---|---|
| id / title / url | 基本 |
| type | `doc`(官方文档) / `tutorial`(教程) / `video`(视频) / `tool`(工具/练习场) / `spec`(规范) |
| language | java / python / node / go / all |
| tech_stack | Spring Boot / MyBatis / React …（可空） |
| concept_tags | 关联概念（CSV 或子表），匹配主键 |
| error_types | 直接关联的异常类型（可空） |
| difficulty | 1=零基础 / 2=有基础 / 3=进阶 |
| authority | 1-5 权威度（官方=5，知名社区=4，个人博客=2） |
| est_minutes | 预计阅读时长（新人最需要这个） |
| description | 一句话说明"这篇能解决你什么疑问" |
| status / sort_order / hit_count | 管理 |

**表 2：`concept`（概念）**

`id / name / alias / plain_definition（人话定义）/ analogy（类比）/ category / language`

**表 3：`concept_edge`（概念前置关系，有向图）**

`from_concept_id / to_concept_id`，含义：**要懂 from，先懂 to**。

示例：`依赖注入 → Spring 容器 → 控制反转`、`空指针 → 对象与引用 → 引用类型`。

#### 3.2.3 匹配与排序算法（`ResourceMatcher`）——本模块技术核心

**四路召回：**

| 召回路径 | 依据 | 离线可用 |
|---|---|---|
| R1 概念召回 | AI 输出的 `concepts[]` ∩ `resource.concept_tags` | ❌ 依赖 AI |
| R2 规则召回 | 异常类型 → 概念映射表 → 资料 | ✅ |
| R3 技术栈召回 | 已识别技术栈 → 资料 | ✅ |
| R4 关键词召回 | 异常类型/语言关键词全文匹配 | ✅ |

**加权打分：**

```
score = 0.45 * 概念命中率
      + 0.25 * 异常类型命中
      + 0.10 * 技术栈匹配
      + 0.10 * 权威度归一化
      + 0.05 * 难度适配（新人版偏 difficulty=1）
      + 0.05 * 历史点击率（hit_count 归一化）
```

**多样性约束：** 同一 `type` 最多 2 条、同一域名最多 2 条，避免全是官方文档或全是一个站。

**分组输出：**

- 「先看这个」1-2 条（最高分 + 难度最低）
- 「延伸阅读」3-5 条
- 「前置概念」按学习路径排（见下）

> **关键设计：R2/R3/R4 都是离线规则，所以即使没有 AI Key（Mock 模式），学习资料推荐依然完整可用。** 这是演示与取证时的保险。

#### 3.2.4 学习路径生成（`LearningPathService`）——第二技术核心

基于 `concept_edge` 有向图，从 AI 给出的目标概念出发，做**反向遍历**，收集全部前置概念，再**拓扑排序**输出学习顺序。

```
输入：concepts = [依赖注入, 空指针]
      ↓ 反向遍历 concept_edge
      [引用类型 → 对象与引用 → 空指针]  [控制反转 → Spring 容器 → 依赖注入]
      ↓ 拓扑排序 + 去重
输出：① 引用类型  ② 对象与引用  ③ 控制反转  ④ Spring 容器  ⑤ 空指针  ⑥ 依赖注入
     每条概念挂 1-2 条最高分资料
```

**防环**：遍历时记录 visited，遇到环直接剪断（种子数据本身应无环，但算法必须防御）。

**这是整套软件里最像"算法"的东西**，也是软著说明书里最有说服力的一节：*概念图谱 + 反向遍历 + 拓扑排序生成个性化学习路径*。

#### 3.2.5 AI 侧的改动

- `OpenAiCompatAIService` 提示词新增受控字段：

```
"concepts": ["理解这个报错需要先懂的概念，只能从给定词表中选择，最多3个"]
```

- **受控词表**从 `concept` 表读出并注入提示词 → 避免 AI 自由发挥产生无法匹配的概念
- 词表为空时降级：不输出 concepts，走 R2/R3/R4 规则召回

#### 3.2.6 前端呈现

**A. 结果卡片新增区块「📚 想彻底搞懂它？」**

```
先看这个
  □ [官方文档] Java 异常处理入门 · 8 分钟 · 零基础
  □ [教程] 什么是空指针？一图看懂 · 5 分钟

学习路径（按顺序补）
  1. 引用类型 →  2. 对象与引用 → 3. 空指针   [展开查看每步资料]

延伸阅读
  · MDN: TypeError 常见原因
  · ...
```

**B. 新增「学习中心」页面**

- 按 语言 / 概念 / 难度 / 类型 筛选，关键字搜索
- 收藏、标记已学、我收藏的
- 概念图谱浏览（可视化可选：先用列表 + 前置关系文字呈现，不做图形库）

**C. 术语气泡**：解释文本中的术语 hover 显示人话定义（复用 `glossary_term`）

#### 3.2.7 种子数据策略（重要，决定质量）

- 目标 **≥120 条资料、≥40 个概念、≥60 条概念关系**
- **只收稳定入口**：官方文档章节页、MDN、知名系统化教程（廖雪峰 / 菜鸟 / 阮一峰 / Real Python / Go by Example / Spring Guides / Node 官方）
- 每条 URL **实现时逐条访问验证返回 200**，不接受 404 与需登录页
- 中文优先；无优质中文资源的补英文官方文档并标注「英文」
- 内容以"能讲清一个概念"为准，不追求数量堆砌

### 13.2 P5：用户体系与数据隔离

**目标**：每个用户拥有独立的报错记录、诊断回填、收藏与学习进度；管理员可管理用户并查看全局调用日志。

**数据表**

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sys_user` | id / username / password_hash / display_name / role(USER,ADMIN) / status / created_at / last_login_at | 用户主表，密码 BCrypt 存储 |
| `user_profile` | user_id / theme / preferred_language / onboarded | 用户偏好（持久化，替代 localStorage） |
| `user_bookmark` | user_id / target_type(resource,concept,history) / target_id / created_at | 收藏与学习进度 |
| `attachment` | id / user_id / history_id / type(image,voice) / path / mime / size / ocr_text | 多模态附件 |

**认证方案**：Spring Security + JWT（无状态）
- 登录返回 token，前端存本地，axios 拦截器统一注入 `Authorization`
- 密码 BCrypt；登录失败限流；token 过期自动跳登录页

**数据隔离方案（本模块技术核心）**

采用 MyBatis-Plus 的 **`TenantLineInnerInterceptor` 多租户插件**，在 SQL 层自动追加 `user_id = ?`，而不是靠每个 Service 手写条件——

```
业务代码：historyMapper.selectList(wrapper)
实际执行：SELECT ... FROM error_history WHERE ... AND user_id = 3
```

- `UserContext`（ThreadLocal）持有当前登录用户，拦截器从中取值
- **公共数据表白名单**（不隔离）：`error_template`、`learning_resource`、`concept`、`glossary_term`
- **私有数据表**（自动隔离）：`error_history`、`history_diagnosis`、`ai_call_log`、`triage_feedback`、`attachment`、`user_bookmark`
- **越权防护**：即使绕过前端菜单，后端也会因租户条件而查不到他人数据（这一点必须写进设计说明）

**持久化**：主题、收藏、已学标记、下一步勾选状态全部落库；迁移前端所有 localStorage 状态。

**管理员能力**：用户列表（含分诊次数统计）、启用/禁用、重置密码、角色调整、跨用户调用日志查询。

**历史数据迁移**：现有 5 条历史记录统一归属到初始化的第一个管理员账号（迁移脚本 `migrate-v30-user.sql`）。

### 13.3 P6：多模态输入（图片 + 语音）

**目标**：vibecoding 用户最常见的场景是"截个图 / 说句话"，而不是手打堆栈。

**统一抽象**：

```
text  ─┐
image ─┼─▶ TriageInput{ rawText, contextText, attachments[] } ─▶ 分诊链路
voice ─┘
```

- `rawText`：报错正文（来自粘贴 / 图片识别 / 语音转写）
- `contextText`：用户补充的场景描述（语音最常见）
- `attachments`：原始图片/音频，按用户隔离存储

**图片输入**

| 环节 | 方案 |
|---|---|
| 入口 | 支持 **Ctrl+V 直接粘贴截图**（最符合直觉）+ 拖拽上传 + 点击选择 |
| 主通道 | 视觉大模型（OpenAI 兼容 `image_url` 消息）→ 一次性输出「报错文本 + 截图场景描述」 |
| 兜底 | OCR（Tesseract 本地 / 云 OCR 可插拔）→ 只取文本 |
| 限制 | ≤5MB；白名单 png/jpg/webp；服务端二次校验 MIME 与文件头 |
| 存储 | `./data/uploads/{userId}/{yyyyMM}/`（按用户隔离目录，防止路径穿越） |

**语音输入**

| 环节 | 方案 |
|---|---|
| 前端 | 浏览器 **Web Speech API**（Chrome/Edge 原生，免费、中文支持好）实时转写，边录边出字 |
| 后端兜底 | Whisper 兼容 `/v1/audio/transcriptions`（不支持的浏览器走上传音频） |
| 用途 | 主要作为**场景补充**："我点保存的时候它就这样了" |
| 隐私 | 音频默认不落库，只留转写文本；可在设置里开启"保留原始音频" |

**Mock 兜底**：无 AI Key / 无 OCR 服务时，图片通道返回"演示模式：识别到的示例文本"，保证全流程可演示。

### 14.2 IM 接入评估（微信 / 飞书 / QQ）

**先说结论：飞书能做、微信限制大、QQ 基本别碰。**

#### 三平台合规性现实（个人开发者视角）

| 平台 | 可行路径 | 门槛 | 结论 |
|---|---|---|---|
| **飞书** | 自建应用 / 群机器人 webhook | 个人可创建免费团队 → 创建自建应用；webhook 模式几行代码即可跑通 | ★★★★★ **可做** |
| **微信** | ①个人微信协议 ②公众号 ③小程序 | 见下 | ★★☆☆☆ **受限，建议延后** |
| **QQ** | ①官方机器人开放平台 ②第三方协议 | ①需企业主体 ②违反用户协议 | ★☆☆☆☆ **不建议** |

#### 微信的三条路，逐个说清

| 路径 | 现实情况 | 风险 |
|---|---|---|
| ① 个人微信协议（itchat / wechaty 等） | 腾讯**未开放个人微信 API**，第三方协议一律违反《微信个人账号使用规范》 | ❌ 封号 + 不可用于登记软件，**直接排除** |
| ② 公众号（订阅号） | 个人主体可注册，但**订阅号没有主动推送能力**，只能被动回复，客服消息接口需服务号（企业主体） | ⚠️ 能力太弱，做不出完整体验 |
| ③ **微信小程序** | 个人主体可注册；可申请**一次性订阅消息**（可实现"分诊完成 → 通知"） | ✅ 唯一合规路径。但需要：**ICP 备案域名 + HTTPS + 类目审核 + 审核周期 2-4 周**，一个月内做不完 |

> **微信的现实结论**：技术上能做的是小程序，但**备案 + 审核的周期不可控**，且需要一台带备案域名的公网服务器。建议放到 V2.1，先解决域名备案这个前置条件。

#### QQ 的现实结论

- 官方 QQ 机器人开放平台：**需要企业主体认证**，个人开发者进不去
- LLOneBot / NapCat 等第三方框架：非官方协议，**封号风险高**，且不合规
- **建议直接放弃**，把精力放在飞书上。

### 14.3 飞书接入设计（推荐方案）

#### 产品形态（两个方向，都做）

```
① 主动提问（手机端输入）
   飞书群里 @机器人 + 粘贴报错/截图
        → 后端分诊 → 机器人回复富文本卡片（6 步解释 + 学习资料链接）

② 被动通知（手机端接收）
   Web 端完成分诊 / 长任务完成 → 推送到绑定的飞书会话
```

#### 技术架构

```
飞书事件订阅(HTTP 回调)
      ↓ 验签 + 解密 + 幂等去重
ImEventAdapter ──▶ 统一消息模型 ImMessage
                     { channel, imUserId, msgType(text/image/voice), content, chatId }
      ↓ 账号绑定（imUserId ↔ sys_user）
TriageInput{ rawText, contextText, attachments }
      ↓ 复用现有分诊链路
ImReplyRenderer ──▶ 飞书交互卡片（Markdown/富文本/按钮）
```

**关键设计点**

| 点 | 说明 |
|---|---|
| 渠道抽象 | 定义 `ImChannel` 接口（`verify() / parse() / reply() / push()`），飞书是第一个实现，后续微信/QQ/钉钉可插拔 |
| 验签与幂等 | 飞书事件会重试，必须用 `event_id` 做幂等表，避免重复分诊重复计费 |
| 富文本卡片 | 用飞书**交互式卡片**而不是纯文本，才能做出"6 步解释 + 可点击学习链接"的体验 |
| 图片/语音消息 | 飞书图片消息给 `image_key`，需调 API 下载 → 复用 P6 多模态通道 |
| 账号绑定 | 首次使用需绑定：机器人生成 6 位绑定码，用户在 Web 端输入，或飞书 OAuth 授权 |
| 公网回调 | 事件订阅需要一个公网可达地址 → 开发期用内网穿透，上线需部署到云服务器 |
| 异步 | 分诊可能 5-30 秒，超过飞书回调时限（3 秒）→ 必须先 ACK 再异步回推 |

**新增表**：`im_bind`（user_id / channel / im_user_id / bound_at）
`im_event`（event_id 幂等）、`im_message_log`（发送记录）

**新增接口**：`POST /api/im/feishu/callback`（事件回调）、`POST /api/im/bind/code`、`POST /api/im/bind`

**工时**：渠道抽象 0.5d + 飞书端到端（验签/卡片/图片/绑定/异步回推）3.5d ≈ **4 人天**

**成本**：开发期需内网穿透；上线需一台公网服务器（或已有部署环境）
